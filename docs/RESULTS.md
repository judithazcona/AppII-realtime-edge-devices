# Results — what was measured, and what was not

Every number here comes from a command that was actually run in this repository, on the
recordings listed in [`data/README.md`](../data/README.md). Anything not measured is written as
**TODO** rather than estimated. Reproduce with the commands in
[`docs/TRAINING.md`](TRAINING.md); the pipeline is seeded (`SEED = 20261109`), so the same
recordings give the same numbers twice.

## 1. Dataset as trained on today

| Class | Sessions | Used for |
| --- | --- | --- |
| `not_attached` | 4 — `table_still`, `hand_loose`, `lap_pocket`, `pickup_putdown` | 2 train / 1 val / 1 test |
| `shaking` | 4 — `gentle_small`, `vigorous_arm`, `side_to_side`, `wobble_rotation` | 2 train / 1 val / 1 test |
| `calm_breathing` | 2 — `calm_sitting` (person Sami), `calm_judith` (person Judith) | 1 train / 0 val / 1 test |
| `fast_breathing` | 2 — `fast_sitting` (Sami), `fast_judith` (Judith) | 1 train / 0 val / 1 test |

Splits are assigned to **whole sessions** before windowing and committed in
[`training/split_assignment.json`](../training/split_assignment.json), so overlapping windows can
never leak between train and test. Two of our own bring-up recordings are on disk but excluded
(`--list` marks them `usable: no`).

**The breathing classes are too small.** Two sessions means one to fit on and one to hold out, so
their held-out numbers are a smoke test of the pipeline, not a performance claim. Everything below
has to be re-run on ≥4 sessions per breathing class, from ≥2 people and ≥2 placements, before any
accuracy is quoted as a result.

## 2. Two-class model (`not_attached` vs `shaking`)

`uv run python training/train.py --classes not_attached,shaking --export`

| Held-out **test sessions** (`lap_pocket`, `vigorous_arm`) | pred not_attached | pred shaking | recall |
| --- | --- | --- | --- |
| true `not_attached` (35 windows) | **35** | 0 | **100 %** |
| true `shaking` (35 windows) | 0 | **35** | **100 %** |

- Validation (`pickup_putdown`, `gentle_small`): **57/69 = 82.6 %** — 10 handling
  windows (picking the board up, putting it down) were read as gentle shaking. Validation is the
  honest number here; the test set was too easy.
- Logistic-regression floor on the same features and the same test sessions: **100 %** — on two
  classes the MLP earns nothing over a linear model. It starts earning its bytes when classes 3
  and 4 are added.
- Held-out **sessions**, never random windows.

## 3. Four-class model, with the breathing-band feature

`uv run python training/train.py --export` → MLP **26-16-4**, ReLU, `alpha=1e-3`, 568
iterations, loss 0.02519, 480 weights = 1.9 KB.

Held-out sessions: `calm_judith`, `fast_judith`, `lap_pocket`, `vigorous_arm`.

| true ↓ / predicted → | calm | fast | not_attached | shaking | recall |
| --- | --- | --- | --- | --- | --- |
| `calm_breathing` (46 w) | **35** | 11 | 1 | 0 | **74 %** |
| `fast_breathing` (47 w) | 0 | **47** | 0 | 0 | **100 %** |
| `not_attached` (35 w) | 9 | 17 | **9** | 0 | **26 %** |
| `shaking` (35 w) | 0 | 0 | 0 | **35** | **100 %** |

**Test accuracy 126/164 = 76.8 %**; validation 56/69 = 81.2 %; logistic-regression floor on the
same features and sessions **76.2 %**.

Reading it honestly:

* `shaking` and `fast_breathing` separate cleanly and survived a held-out person (Judith's
  sessions were never fitted on).
* **`not_attached` is the failure.** The held-out `lap_pocket` session — the board in a lap pocket
  on a sitting person — is read as breathing in 26 of 35 windows. A board carried on a person moves
  like a board on a chest, and two takes per breathing class cannot express the difference. This is
  the single result that decides what to record next.
* `calm_breathing` leaks into `fast_breathing` in 11 windows, i.e. the band feature separates
  breathing from rest but not yet calm from fast reliably.
* Before the band feature existed, the same four-class split scored **50.0 %** and the held-out
  `not_attached` session went to breathing 35/35 — the two `bb_*` features are worth
  ~27 points of held-out accuracy, which is why they are in the firmware too.

## 4. Determinism and export

* Same command twice → **byte-identical** metric block (seed rule holds).
* `firmware/model_weights.h` is regenerated by the training script and re-read afterwards,
  forward-propagated in numpy and compared with sklearn: **max |Δp| = 1.6e-07** (four-class),
  **7.4e-10** (two-class). That proves the weights survived serialisation.
* **It does not prove the chip computes the same features.** See TODO below.

## 5. On the board

Measured through the temporary `firmware/debug_pipeline` build (same `config.h`, `features.h`,
`model_infer.h`, window logic and BLE as the demo sketch, plus USB logging):

```
[tick]  uptime=93000 samples=9243 hz=99.86 read_fails=0 state='not_attached'
[feature] mag_std=0.00240 ax_jerk=0.00161 gmag_mean=1.3046 bb_energy=0.000162 bb_ratio=0.06533
[model]   p=[0.0377 0.0031 0.9589 0.0004 ] winner=not_attached
[state]   agreed, state stays not_attached
[ble]    heartbeat value='not_attached' subscribed=0 notify=OK total=92
```

* Sensor read at **99.86 Hz** with **0 read failures** over 9243 samples.
* Features, probabilities, the two-window vote and the committed state all fire; the committed
  state is what BLE transmits, notified once per second and on every change.
* With the board lying still on the desk the pipeline answers `not_attached` at p ≈ 0.96 — which
  is the correct label for that state, and the explanation for a BLE value that "never changes"
  while nobody moves the board.
* **One real defect found and fixed here:** I²C dropouts stretch a 2.5 s window to 6–10 s, which
  scales every rate-like feature down ~3× and makes the model answer at random. The demo sketch
  now refuses a window that took more than 1.5× its nominal time, clears the decision and blinks
  amber instead of guessing.

Flash / RAM, FQBN `esp32:esp32:esp32s3:FlashMode=dio,FlashSize=16M,PSRAM=disabled,CDCOnBoot=default`:

| Sketch | Flash | RAM |
| --- | --- | --- |
| `classifier` (no BLE, 2-class model) | 323 042 B (24 %) | 29 664 B (9 %) |
| `classifier` (4-class model) | 327 578 B (24 %) | 29 664 B (9 %) |
| `classifier` + BLE | 578 857 B (44 %) | 40 172 B (12 %) |
| `debug_pipeline` (BLE + logging) | 590 337 B (45 %) | — |

## 6. Not measured — TODO, in the order that loses the fewest points

1. **Feature parity on the chip.** One window fed through `features.h` and diffed against
   `features.py`; nothing proves yet that the board computes the vector the model was trained on.
2. **A live client watching notifications.** `notify()` returns OK and the value is the classifier
   output, but no BLE client has been observed receiving it — the GitHub Pages monitor page does
   not exist yet, and the phone app reported the CCCD disabled.
3. **Four colours on the LED** with a model trained on ≥4 breathing sessions.
4. **Power-bank boot** with the data cable out of the laptop (the firmware never waits for a host,
   but the acceptance test is the board running on a battery, which has not been performed).
5. **Inference time per window and free heap** — not instrumented.
6. **Board's own Wi-Fi page** and the **abstention extension** (steps 9 and 10 of
   [`PLAN.md`](../PLAN.md)): not started, so no numbers.
